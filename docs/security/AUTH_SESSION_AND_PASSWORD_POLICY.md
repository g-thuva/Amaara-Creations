# Authentication, sessions and password policy

## New credentials and existing accounts

Continue ASP.NET Core Identity hashing and existing stored hashes. New registration, reset and change-password operations validate 15–128 Unicode code points with a 256 UTF-16-unit API bound. No uppercase/digit/punctuation composition rule, forced periodic rotation or paste blocking is added. Existing shorter passwords can still sign in, avoiding an account lockout migration. A local whole-password blocklist and configurable `Authentication:BlockedPasswords` reject common choices; this is not comprehensive breach-corpus verification. NFC is used for blocklist comparison, not a silent rehash/normalization migration of existing passwords.

Password visibility is local display state only. Every password field in the shared sign-in and account settings uses PasswordField; inputs remain masked by default with current/new autocomplete, a keyboard-operable visibility button, Caps Lock hint and a 30-second/window-blur rehide. Guidance is length-based and does not claim to measure password entropy or confirm breach status.

Duplicate registration now uses the same successful response as a new registration. Login errors remain generic except the existing email-verification guidance after a correct password. Forgot/reset flows preserve verified expiring Identity token processing. Data-protection reset/verification tokens expire after 30 minutes; password reset/change updates the stamp and revokes refresh sessions.

## Sessions and revocation

Access JWTs remain in memory, not new localStorage/sessionStorage token persistence. Refresh tokens are random, hashed server-side, rotated, replay-detected and sent in HttpOnly cookies. Production cookies are Secure, SameSite=Lax and scoped to `/api/v1/auth`. All state-changing authentication methods reject untrusted Origin values and cross-site browser requests with no Origin; approved origins are exact configuration values. This design requires same-site frontend/API deployment for the Lax cookie flow.

All users enter credentials through shared `/api/v1/auth/sign-in`; pending staff complete protected verification or enrollment before any JWT/session issuance. Management retains its dedicated `/api/v1/auth/staff/refresh`, `/logout` and authenticated `/session` response. Legacy login aliases delegate to the same service. Its separately named refresh cookie is additionally protected with a distinct Data Protection purpose and scoped to `/api/v1/auth/staff`; public raw refresh cookies cannot be replayed there. Management cookie exchanges and session inspection accept only `Administration:AllowedOrigins`, including rejection of the otherwise approved storefront origin. Staff policies require a server-issued `session_kind=management` claim as well as current roles and recent MFA. Completed shared staff sign-in creates independent shopping/management families and navigates to the approved management entry. Only a shopping token is returned to the storefront; management restores its own cookie through its approved origin and verifies current permissions before loading operations. Logout is application-specific; logout-all, password changes and MFA replacement revoke all relevant server families.

Every access token carries the user's current security stamp and a refresh-session family. Bearer validation checks signature/HS256, JWT token type, issuer, audience, expiry, stamp, account availability and an unrevoked/unexpired family, then replaces claimed roles with current database roles. Logout revokes the family; logout-all changes the stamp and revokes all families. Existing pre-change access tokens lack binding and must sign in again after rollout.

## Staff assurance

Staff APIs are closed unless `Administration:Enabled=true`. A correct enrolled Identity authenticator code adds MFA assurance to the server-minted token. Incorrect factors increment the same account lockout counter without a correct password resetting it first. Rate limiting applies to login.

A separate data-protected HttpOnly assurance cookie contains only user/stamp/family/original verification time. Refresh accepts it only for that same active family/user/stamp and within 15 minutes. Rotation preserves the original time; it never slides the MFA window. Sensitive policies expire at 5 minutes. Missing/expired staff assurance or incomplete enrollment causes refresh to revoke the rotated token and return 401, including old limited sessions. These fixed maximum lifetimes also bound inactivity; there is no long-lived privileged session renewal. The staff shell verifies capabilities before importing operational modules.

First-time staff enrollment is part of the ten-minute password-verified pending transaction: one stable local QR/manual key, native Identity TOTP confirmation, then recovery-code acknowledgment and direct sign-in. No repeated password or extra code is required. Sensitive account-security changes still require password and the existing factor or verified recovery. Confirmation protects the Identity key, rotates the stamp and revokes prior sessions. Native .NET 8 Identity uses 30-second steps and accepts the current step plus two either side (about ?60 seconds); keep clocks synchronized. Accepted codes are consumed once under a SQL per-user lock; protected replay hashes last three minutes. Ten random recovery codes are stored as protected hashes and consumed atomically; the encrypted five-minute acknowledgment transaction supports safe reload. Recovery permits verified replacement, never staff policy assurance before a new authenticator is confirmed. Staff cannot disable mandatory MFA. Individual device families can be listed/revoked without exposing raw tokens or IP addresses. See [architecture](mfa-architecture.md), [setup](staff-mfa-setup.md) and [recovery](mfa-recovery.md).

Verified email change uses a 30-minute Identity token delivered to the new address, password/current-factor reauthentication and transactional address/username update. Tokens are pasted into Security rather than put in URLs. Old sessions are revoked and security notification delivery uses the configured email adapter. Captured transports do not prove genuine SMTP delivery.

The approved offline corpus boundary uses NFC-normalized whole-password SHA-256 buckets with checksums, bounded reads and binary search. A missing/corrupt configured corpus rejects new credentials. Existing hashes/sign-in remain unchanged. The actual corpus and refresh process must be approved; the built-in short list alone is not comprehensive breach coverage.

Remaining release requirements: approved real staff provisioning, private identity-aware hosting, durable protected key-ring/backup custody, real security-alert delivery and recovery operations, corpus approval/refresh and phishing-resistant passkeys where feasible. Production administration defaults to disabled until owner/operator verification; private local activation is documented separately. Disposable TOTP and email-capture endpoints exist only in the separate acceptance executable.
