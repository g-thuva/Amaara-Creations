# Shared login and staff MFA

The public `/login` and `/register` pages serve customers, administrators and staff. Staff workspace links redirect unauthenticated visitors to the shared page, preserving a validated management return path. Signup, password reset and verification use the shared account pages. Signup creates only a Customer identity; staff roles continue to require authorized provisioning.

`GET /auth/sign-in` reports `credentials` for an anonymous browser, `session` when a refresh cookie is present, or the pending MFA stage. The frontend renews only when a session cookie is available. A fresh login page therefore does not produce expected-but-noisy authentication failures. Invalid credentials, rejected refresh tokens and expired challenges still return their appropriate errors.

`POST /api/v1/auth/sign-in` and `/login` accept eligible accounts after password, confirmed-email and lockout checks. Known privileged roles, including mixed Customer/staff memberships, receive an opaque HTTP 202 challenge. They receive no access token or refresh family before successful authenticator verification. Unenrolled staff follow the existing enrollment and saved-recovery-code acknowledgment flow. Deliberately enabled customer MFA remains supported.

Credential entry and session scope are distinct decisions. `AppRoles.CanBeginSignIn` allows either eligible identity at the shared entry. `CanSignIn` continues to restrict refresh and bearer sessions to their correct application scope. Challenge verification binds the original entry, nonce, current roles, stamp, expiry and lockout state; moving a challenge cookie between shared and compatibility staff endpoints fails.

After required verification, current server roles select exactly one session: storefront for customers, management for staff. Staff tokens require MFA and retain existing server-side permission checks. The shared page does not install a staff token as its shopping identity or persist credentials in browser storage. It navigates to the configured management app, which restores the HttpOnly staff cookie and verifies `/auth/staff/session` before loading permitted operational routes. Navigation carries no password, code, access token or refresh credential.

Starting shared staff MFA preserves an independent customer cookie. Customer and staff refresh/logout remain separately scoped, and the storefront origin cannot exchange management cookies through staff endpoints. Existing exact CORS/Origin protections, session lifetimes, sensitive-action MFA freshness and revocation are retained. Configure `VITE_MANAGEMENT_LOGIN_URL` for the shared app and `VITE_PUBLIC_SITE_URL` for the management app; local development uses storefront 5179, management 5173 and API 5192.

Verification covers all seven privileged roles, customer login, shared login aliases, pending restoration, entry-bound challenges, invalid/expired/replayed MFA, enrollment/recovery and application permissions. Browser journeys cover a single password entry followed by MFA on the shared page, dashboard arrival and reload, specialist routing, customer login, independent sessions, setup cancellation and forged browser roles.
